## Memory (M-1)

One `db.transaction(fn)` with 20,000 single-row `INSERT`s into `tag` through `tx.execute()`, each mode in its own process with `--expose-gc`. "Held before commit" is the heap after a forced garbage collection at the end of the callback, minus the heap before the transaction. "Peak" is sampled every 20 ms and every 500 inserts, so it is approximate. The third row is a middleware with only an empty `activityFinalized` hook, to see where the cost comes from.

| Middleware | Held before commit | Per statement | Peak above start | After commit |
|---|---|---|---|---|
| none | 1.1 MB | 56 bytes | 58.6 MB | 0.7 MB |
| `createCacheMiddleware()`, no annotation | 55.4 MB | 2,905 bytes | 100.9 MB | 0.9 MB |
| empty `activityFinalized` only | 50.0 MB | 2,619 bytes | 94.7 MB | 0 MB |

So registering the cache makes a transaction hold about 2.9 KB per statement until it ends, even when no write is annotated: about 55 MB for 20,000 statements, and in proportion about 2.8 GB for a million. Almost all of it comes from the runtime keeping finished statements for finalization, not from the cache itself: an empty `activityFinalized` hook costs nearly the same. All memory is released at commit. Run times (89 s, 73 s, 81 s) are PGlite on a loaded machine and say nothing about speed. The README's "Cost" bullet describes this, but gives no size (Q4-6).

## Findings

### Q4-1: without the client's `log` option, a failed invalidation leaves no trace

Severity: medium. The cache README says a write whose annotation has `meta` on the default store "logs `RUNTIME.CACHE_STORE_META_UNSUPPORTED` ... Nothing fails, so check the logs." The same goes for any store error. But `postgres()` drops these events unless the app passes `log` (the Postgres README says so; the cache README does not). The demo's client passes no `log`. So in the demo, or any app set up like it, an annotated write that cannot invalidate succeeds silently, and reads keep serving the old value until it expires (`extras.log`, E-2b). The cache README should say that these errors reach only the client's `log`, and link to it. A user cannot see the failure any other way.

### Q4-2: the demo does not show invalidation with a write

Severity: low. The demo README's "Cache Middleware Examples" has three read commands and nothing on `invalidateAnnotation` or `invalidate`. Its list of points still describes caching only. A short command that caches a read, runs an annotated update and reads again would show the feature, as the other cache commands do.

### Q4-3: the error for the annotation on a read states the rule but not the fix

Severity: low. At run time: "Annotation 'cache-invalidate' is not applicable to 'read' operations (terminal: 'first'). The annotation declares applicableTo = ['write']." The error has no `fix` field. It does not say "annotate the write that changes this data instead, or call `cache.invalidate()`". The builder case names the terminal `'sql-dsl.annotate'`, which is not a name the user wrote. At compile time the message is "Argument of type 'AnnotationValue<InvalidateAnnotationOptions<unknown>, "write">' is not assignable to parameter of type 'never'", which does not mention reads or writes. Both are the same shape as the existing errors for `cacheAnnotation` on a write.

### Q4-4: the error for `meta` on the default store does not say what to do

Severity: low. "The in-memory cache store cannot remove entries by meta because it does not index meta." It does not say that the `keys` in the same call were not removed either, or that the fix is a store that indexes `meta` or `keys` alone. The README says both; the log line does not.

### Q4-5: a rolled-back transaction still ends `succeeded` (slice-1 Q-5, still open)

Severity: low, not new. In W-4 and W-6e the tracer shows `ended transaction#1 outcome=succeeded` and then every activity finalized `rolled-back`. The invalidation uses the finalized outcome, so it behaves correctly.

### Q4-6: the README does not say how much memory the cache adds to a long transaction

Severity: medium. Measured in M-1: with the cache registered, a transaction holds about 2.9 KB per statement until it ends, whether or not any write is annotated, against 56 bytes without middleware. A batch job that runs a million statements in one transaction would hold close to 3 GB. The README's "Cost" bullet says memory "grows with the number of statements it runs" but gives no size, and nothing tells an app that caches reads, but never annotates writes, that it pays this. The cost is the runtime's finalization tracking: any middleware with `activityFinalized` causes it. A size in the README, and advice for long batch transactions (for example a separate client without the cache), would let users plan for it.
