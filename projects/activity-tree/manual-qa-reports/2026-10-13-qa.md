## Findings

### Q-1. When one middleware's `activityEnded` throws, the middleware after it never receive `activityEnded`, and the activity is finalized `committed`

Severity: high. This is new behavior in this slice, and nothing documents it.

Reproduction:

1. Register `middleware: [budgets({ maxLatencyMs: 200 }), observer]` on `postgres<Contract>({ contractJson, url })`. `observer` logs each of the three lifecycle events.
2. Run `db.runtime().query(db.raw.sql\`select pg_sleep(0.3)::text as slept\`.returnsRow({ slept: 'pg/text@1' }).build()).toArray()`.
3. Script: `wip/qa/budgets-order.ts`. Output:

```text
observer started statement
observer finalized statement committed
caller rejected BUDGET.TIME_EXCEEDED
```

What is wrong:

- ADR 271 says "every activity is started, then ended, then finalized". For `observer`, this activity starts and is finalized, but it never ends. The ADR and the subsystem doc spell out this skip only for `activityStarted`.
- ADR 271 says an activity with no enclosing transaction is finalized "`unknown` when it failed". The caller received an error, yet the activity is finalized `committed`.
- The demo hits this. `src/prisma/db.ts` registers `budgets({ maxLatencyMs: 1_000 })` before `slowQueryWarning({ thresholdMs: 250 })`. So a statement slower than 1 s never reaches the slow-query warning, and those are the statements the warning exists for.

Recommendation: run every middleware's `activityEnded` even after one throws. Report the first error to the caller. Then either finalize the activity `unknown`, or say in ADR 271 that a statement failed after the database succeeded is finalized `committed`.

### Q-2. An application author cannot see anything middleware writes to `ctx.log`

Severity: medium. This was already true on `main`, but this slice relies on it more.

Reproduction: run a 300 ms statement through the demo's `slowQueryWarning({ thresholdMs: 250 })` on a `postgres()` client (check A-7 in `wip/qa/tracer.ts`). Nothing is printed. `PostgresExecutionOptions` has no `log` field, and `SqlRuntimeBase` defaults to `noopLog` (`packages/2-sql/5-runtime/src/sql-runtime.ts`).

Effects:

- The demo README says the slow-query middleware "logs a warning past the threshold". A user who runs the demo never sees one.
- ADR 271 says an error thrown from `activityFinalized` "is passed to `ctx.log.error`". With `postgres()` it is silently dropped (check B-11).
- The same applies to budget warnings and to the `middleware.activityEnded.error` event after a rollback.

### Q-3. `budgets()` warn severities cannot be used from `postgres()`

Severity: medium. This was already true on `main`. This slice turns the observed-row check on, so it now matters more.

Reproduction: `budgets({ maxRows: 1, tableRows: { user: 1 }, severities: { rowCount: 'warn', latency: 'warn' }, maxLatencyMs: 200 })`, then read `limit 5` from `user`, and run `pg_sleep(0.3)`. Both reads throw (`BUDGET.ROWS_EXCEEDED`, `BUDGET.TIME_EXCEEDED`). `budgets()` blocks whenever `ctx.mode === 'strict'`, and `postgres()` has no `mode` option (Mongo's client has one).

Effects:

- The upgrade instructions say that with `'warn'` in `permissive` mode, the observed-row check logs one warning and keeps streaming. A `postgres()` user cannot get there.
- The default latency severity is `'warn'`, yet the demo's `maxLatencyMs: 1_000` makes any statement slower than 1 s throw.

### Q-4. The docs disagree about `source` when `beforeEncode` blocks a statement

Severity: low.

Reproduction: `db.runtime().execute(db.sql.public.user.delete().build())` with `lints()` (check B-5). The statement ends `outcome=failed latencyMs=0 source=driver`.

The upgrade instructions say a statement that fails before it runs ends with `source: 'driver'`, which matches the behavior. But `docs/architecture docs/subsystems/4. Runtime & Middleware Framework.md` (line 240) says `source` is `'middleware'` "when an interceptor supplied the result or threw", and ADR 271 lists `beforeEncode` as an interceptor. A reader also finds `'driver'` odd for a statement that never reached the driver.

### Q-5. A rolled-back transaction ends `succeeded`

Severity: low.

Reproduction: `db.transaction(async (tx) => { await tx.query(...).toArray(); throw new Error('x'); })` (check B-4). The tracer shows `ended transaction#1 outcome=succeeded`, then every activity finalized `rolled-back`.

This is the specified behavior: the outcome describes how `rollback()` settled. But the upgrade instructions never describe a transaction's `activityEnded` result. A middleware author who reads "`succeeded`, `failed` or `stopped`" will expect a failed callback to end `failed`. Add one sentence: a transaction's outcome says whether its `COMMIT` or `ROLLBACK` call settled; read `activityFinalized` to learn whether it committed.

### Q-6. The upgrade instructions use `ActivityContext` but do not say where to import it

Severity: low.

The `WeakMap`-to-`ctx.state` example declares `function pendingOf(ctx: ActivityContext)`. `ActivityContext` is not exported from `@prisma/orm-postgres/family-runtime`, the entry point the demo's middleware imports from. It is only exported from `@prisma/orm-framework/components/runtime`. A SQL middleware author can use `SqlMiddlewareContext`, which that entry point does export. The instructions should name the import, or use `SqlMiddlewareContext` in the SQL example.

### Q-7. The demo's `pnpm emit` and `pnpm db:init` fail

Severity: low. This is not caused by this slice.

Reproduction: in `examples/prisma-8-demo`, run `pnpm emit`. Output: `sh: prisma: command not found`. The demo depends on `@prisma/cli-engine`, which ships no `prisma` binary. The workaround is `node ../../packages/1-framework/3-tooling/cli/dist/bin.mjs contract emit` (and `db init`).

### Q-8. The demo README's cache example uses a user id that the seed never creates

Severity: low. This is not caused by this slice.

The README runs `pnpm start -- cache-demo-user 00000000-0000-0000-0000-000000000001`. `pnpm seed` creates users with random ids, so that command reads no row. The README should say to use an id that the seed prints.
