## Findings

### Q2-1. The upgrade instructions do not show an extension how to start, use and end its own activity

Severity: medium.

The instructions open by saying a client starts an activity with `startActivityOn(queryable, activity)`, and that a middleware can use `intercept.onActivity`. After that they only cover renames and passing the members through a facade. An extension author who wants their own kind has to find the rest in the subsystem doc. Missing from the instructions:

- an example of `startActivityOn`, `handle.intercepted`, `handle.query`, `handle.end({ outcome, result })`;
- the signature of `intercept.onActivity(activity, ctx)` and that it returns `{ result }` or `undefined`;
- that a handle must always be ended, or `close()` never settles (see Q2-2);
- that `planContentHashOn` is how to derive `contentHash`;
- which packages to depend on. The instructions name `@prisma/orm-framework/components/runtime` and `@prisma/orm-family-sql/runtime/internal/prepared-query`. A `postgres()` user has neither as a dependency; `@prisma/orm-postgres` re-exports both as `components/runtime` and `family-runtime/internal/prepared-query`. Both paths work, including for module augmentation (`wip/qa2/aug-postgres.ts`).

Reproduction: read `upgrade-instructions/pending/client-activities/extension/instructions.md` and try to write `wip/qa2/report-run.ts` from it alone.

Recommendation: add a short "Start your own activity" section with the C-1/C-2 code from `wip/qa2/report-run.ts` (`runReport` and `reportCache`).

### Q2-2. A handle that is never ended makes `close()` hang with no visible warning, and the Node process can exit silently

Severity: medium. The hang is documented behavior. The invisible warning is slice-1 Q-2 again.

Reproduction:

1. In `wip/qa2/report-run.ts`, start an activity and do not end it: `await startActivityOn(db.runtime(), { kind: 'report' as 'report-run', contentHash: 'x' })`. (My first run did this by mistake in E-3b.)
2. Later call `await db.close()`.
3. Output (`wip/qa2/run-1.log`): nothing after the line before `close()`, and the process exits with code 0. `close()` never settles; once the pool is idle nothing keeps the event loop alive, so Node exits and the rest of `main()` never runs.

The subsystem doc says `close()` logs `runtime.close.waiting-for-activities` through `ctx.log.warn`. `postgres()` has no `log` option, so the runtime uses a no-op log and the author sees nothing. A unit test (`packages/2-sql/5-runtime/test/client-activity.test.ts`) shows the warning is emitted with an injected log.

Recommendation: let `postgres()` (and SQLite and Supabase) take a `log`, or print this warning by default. Say in the upgrade instructions that every handle must be ended, for example in a `try`/`finally`.

### Q2-3. The docs name different modules to augment

Severity: low.

- The upgrade instructions augment `@prisma/orm-framework/components/runtime`. That works.
- The subsystem doc ("Client activities", "Kinds") and the slice spec augment `@internal/framework-components/runtime`, which an extension author cannot import.

Recommendation: use the public path in the subsystem doc, or say both.

### Q2-4. A middleware does not see the registered result type

Severity: low. This matches the design, but the instructions suggest otherwise.

Reproduction: `wip/qa2/types-check.ts`. In `activityEnded`, after `if (result.kind === 'report-run')`, `result.result` is `unknown`, not `{ emails: readonly string[] } | undefined`. `Activity` and `ActivityEndedResult` use `ClientActivity` with the default kind `${string}-${string}`, so narrowing on a literal kind does not reach the registry.

The upgrade instructions say "A package that wants a typed result for its own kind registers it". A middleware author will expect the type in their hooks. The registry types only the handle side (`intercepted.result`, `end({ result })`). A middleware must cast or check the value, as `wip/qa2/report-run.ts` does.

Recommendation: say in the instructions that the registry types the handle, and that middleware receive `unknown` and must check it.

### Q2-5. The run-time checks are narrower than the docs suggest

Severity: low.

- A kind without a hyphen is accepted at run time. `startActivityOn(db.runtime(), { kind: 'report' as 'report-run', contentHash: 'e3b' })` starts, ends and finalizes an activity of kind `report` (E-3b). The docs say "a client kind contains a hyphen", and only `'statement'` and `'transaction'` are rejected at run time. A middleware that tells client kinds apart by the hyphen would treat `report` wrongly. Either reject kinds without a hyphen too, or say the hyphen is a type-level rule only.
- `planContentHash` on an ended handle resolves (E-2). The docs list what an ended handle rejects and do not list `planContentHash`, so this is consistent, but a reader may expect it to reject too. One sentence would settle it.

### Q2-6. Comparing `planContentHash` with `ctx.contentHash` needs knowledge the docs do not give in one place

Severity: low.

The subsystem doc says `planContentHash` "returns the digest `ctx.contentHash` gives the statement the plan sends". `ctx.contentHash` is a function, `contentHash(exec): Promise<string>`, and a middleware has the execution plan only in `intercept.onQuery`, `intercept.onExecute` and `beforeEncode`. My first tracer read `String(ctx.contentHash)` in `activityEnded` and got the function's source text (`wip/qa2/run-1.log`, C-8). With `await ctx.contentHash(plan)` in `onQuery` and `onExecute`, the digests are equal.

Recommendation: write "the digest `ctx.contentHash(exec)` returns for the statement's execution plan".

### Q2-7. The `RUNTIME.ACTIVITY_CHILDREN_OPEN` message says "1 activities"

Severity: low.

Reproduction: E-1. Message: "The 'report-run' activity ended while 1 activities beneath it had not ended". The open child is a statement, which the docs also call an activity, but "1 activities" reads wrong. Use "1 child" or "1 activity" with the right plural.
