# Slice: 05-aggregate-codec-typing-and-extension-testkits

_(Parent project `projects/codec-json-projections/`. Outcome this slice contributes: aggregates — the last codec-blind read path — resolve, project, and decode through descriptor-owned output codecs with emitted types in lockstep, and the database-backed conformance harness becomes public dev-only testkit packages for extension authors.)_

## At a glance

After the slice-4 hard cut, every JSON entry with a known codec projects canonically — except aggregates, which the emission tests whitelist as `native` and whose results reach users as whatever the driver sent (`COUNT(*)` arrives as text `'2'` and is `Number()`-coerced, silently lossy past 2^53). This slice introduces `SqlAggregateDescriptor` contributions and registries, emits `aggregateTypes` into SQL `TypeMaps` from the same descriptors, decodes top-level, grouped, and include aggregates through resolved output codecs, and extracts the codec-conformance harnesses into `@internal/postgres-codec-testkit` and `@internal/sqlite-codec-testkit`.

## Chosen design

The settled model is [`design-notes.md` § Aggregate descriptors and emitted aggregate types](../../design-notes.md) and § Conformance testkits; this section grounds it in the current code.

### Aggregate descriptors and resolution

`SqlAggregateDescriptor` maps `(aggregate operation, optional input CodecRef)` to `output CodecRef + nullability + lowered expression`. Input matching supports no-input operations (`count(*)`), exact codec IDs, codec traits, and — amended 2026-07-31 during D2, when execution surfaced that `count(x)` matches nothing under the first three kinds — an input-agnostic kind for operations whose result codec does not depend on their input: such a descriptor matches with or without an input, its output must name a concrete codec (`self` has no referent), and it is consulted after exact and trait matches. Exact matches win over traits; traits win over input-agnostic. Output codec identity is declarative — `self` or a concrete codec ID, with a function permitted to resolve only output type parameters. Lowering may build AST but cannot select a different output codec than declared. (Amendment rationale: `count(x)` is int8/INTEGER on both targets regardless of input; one input-agnostic descriptor models that fact declaratively, where the alternatives — per-trait count descriptors, or the lane special-casing count as input-free — either inflate the matrix or put operation knowledge in a generic planner. The kind lands with D3, which authors the first descriptor needing it.)

Targets contribute descriptors through the component system the way codec descriptors already flow: a contribution key beside `codecDescriptors` on the component `types.codecTypes` surface (collected and single-contributor-validated in `ControlStack`, `packages/1-framework/1-core/framework-components/src/control/control-stack.ts`), assembled once into a validated registry at adapter/runtime composition (`packages/2-sql/5-runtime/src/sql-context.ts`, beside `buildCodecDescriptorRegistry`), and exposed to planners via `QueryLaneContext` beside `codecDescriptors` (`packages/2-sql/4-lanes/relational-core/src/query-lane-context.ts:84`).

The breaking result baseline, verified against real databases rather than inferred from traits:

| Target | Aggregate | Output codec | Application value |
| --- | --- | --- | --- |
| PostgreSQL | `count(*)` | `pg/int8@1` | `bigint` |
| PostgreSQL | `sum(int2\|int4)` | `pg/int8@1` | `bigint` |
| PostgreSQL | `sum(int8)`, integer `avg` | `pg/numeric@1` | decimal string |
| SQLite | `count(*)` | `sqlite/bigint@1` | `bigint` |

The complete PostgreSQL and SQLite matrices (every built-in aggregate × input codec family, including min/max identity and float/numeric/temporal inputs) are enumerated by executable probes during implementation and pinned as database-backed conformance tests.

### Emitted `aggregateTypes`

SQL `TypeMaps` (`packages/2-sql/1-core/contract/src/types.ts:98-112`, six keys today) gains `aggregateTypes`, generated by the emitter (`packages/1-framework/3-tooling/emitter/src/generate-contract-dts.ts`) from the same descriptor contributions the runtime resolves against. ORM aggregate availability and result types resolve against this map with the same exact-over-trait precedence, so emitted types and runtime decoding cannot disagree.

### ORM planning and decoding

- `toAggregateProjection` (`packages/3-extensions/sql-orm-client/src/query-plan-aggregate.ts:24-60`) currently stamps `codec: undefined` for count/sum/avg and the input column codec only for min/max. It resolves through the aggregate registry instead, so `ProjectionItem.codec` is authoritative for every aggregate output (project DoD item; both `compileAggregate` and `compileGroupedAggregate` call sites).
- Include reducers (`buildIncludeChildScalarSelect` / `buildIncludeAggregateExpr`, `packages/3-extensions/sql-orm-client/src/query-plan-select.ts:1150-1330`) pass no codec today, which is why `jsonEntryProjection` falls through to `NativeJsonValueProjection`. They stamp the resolved output codec, so include aggregate JSON entries become codec-projected (large include counts stop corrupting as JSON numbers) and decode through `decodeJson` at extraction (`collection-dispatch.ts:639-654`).
- The `Number()`-coercion shims — `normalizeAggregateResult` (`collection-aggregate-result.ts`) and its duplicate `coerceAggregateValue` (`grouped-collection.ts:240-263`) — are deleted; decoding flows through the generic codec decode path (`packages/2-sql/5-runtime/src/codecs/decoding.ts`), which already short-circuits only when no codec is registered.
- ORM result types (`AggregateSelector` surfaces in `sql-orm-client/src/types.ts:556-585`, `count(): AggregateSelector<number>` today) resolve from `aggregateTypes`.

### sql-builder lane

`CountField` hardcodes `codecId: 'pg/int8@1'` in the target-agnostic sql-builder lane (`packages/2-sql/4-lanes/sql-builder/src/expression.ts:122`, runtime at `src/runtime/functions.ts:168-173`), and `numericAgg` propagates the input codec ID through sum/avg, which is wrong under widening. Both resolve through the aggregate registry available on the lane context; the hardcoded ID goes away (project non-goal: no codec-ID knowledge in generic planners). The static `bigint` typing of `CountField` stays, since both targets' count codecs agree on the application type.

### Conformance testkits

The harnesses currently live as test-internal files (`packages/3-targets/6-adapters/postgres/test/codec-conformance/{harness,cases}.ts`, sqlite equivalent) that pgvector and arktype-json import via `../../../3-targets/...` relative paths across package boundaries. They move to `@internal/postgres-codec-testkit` and `@internal/sqlite-codec-testkit`: published, dev-only, test-framework-independent packages (publishing metadata per `@internal/target-sqlite`, content conventions per `@repo/test-utils`). Built-in adapter suites and both extensions consume the packages; the cross-package relative imports disappear. The aggregate conformance matrices extend the same harness. Production adapters gain no dependency on the testkits.

## Coherence rationale

The transitional-shape constraint pins this as one coherent aggregate hard cut: emitted `aggregateTypes`, ORM/builder result types, and runtime decoding must flip together so no merged state types a result codec the runtime does not honour. The testkit extraction rides in the same PR because the aggregate matrices extend the very harness being extracted — splitting them would churn the same files across two reviews. One reviewer holds one system: a descriptor protocol, its three consumers (emitter, ORM, sql-builder), and its packaging.

## Scope

**In:** the `SqlAggregateDescriptor` type and contribution/registry plumbing (framework-components contribution key, relational-core lane registry, sql-runtime assembly); PostgreSQL and SQLite built-in aggregate descriptor sets; `TypeMaps.aggregateTypes` and its emission; ORM aggregate planning, availability/result types, and decode paths (top-level, grouped, include reducers); sql-builder aggregate functions; the two testkit packages and migration of built-in and extension conformance suites onto them; database-backed aggregate matrices for both targets; regenerated contracts/fixtures; docs and upgrade instructions.

**Out:** new aggregate operations or `having` semantics (project non-goal); Mongo (no aggregate-descriptor or projection change); PostGIS canonical form (TML-3105); explicit-codec-ref diagnostics (TML-3114); the `| Date` authoring-union residue (TML-3110); optimized PostgreSQL array projections beyond the reference lift; SQLite stored scalar arrays; shipping an extension-owned aggregate descriptor (the mechanism is proven by registry tests, not by inventing a pgvector aggregate).

## Pre-investigated edge cases

| Edge case | Disposition | Notes |
| --------- | ----------- | ----- |
| Driver wire shapes differ per target: node-postgres/PGlite return `int8` as text on the top-level wire path, better-sqlite3 returns JS `number` (or `bigint` in safe-integer mode) | Decode top-level values through `codec.decode` (wire) and include values through `codec.decodeJson`; matrices run on both targets | The existing split in `decoding.ts` already distinguishes the channels |
| Empty-set aggregates: top-level `{ count: 0, total: null, avg: null }`; include `emptyScalarResult` returns `0` for count | `count` → `0n`; nullability is descriptor-declared, not inferred | Pinned by `test/integration/test/sql-orm-client/aggregate.test.ts:90-93` and `collection-dispatch.ts:698-699` |
| Three distant test suites pin the current lossy behaviour: `collection-aggregate-result.test.ts` (Number-coercion incl. `'not-a-number'` passthrough), `grouped-collection.test.ts` (duplicate coercion), `test/integration/test/sql-builder/group-by.test.ts:18` (`expect(alice!.cnt).toBe('2')`) | All renegotiated to the breaking baseline, not preserved | group-by.test.ts is the in-repo witness of ROADMAP § 1's aggregate remainder |
| Prisma 7 ports suites assert `number` aggregates (`legacy-aggregations`, `methods-count`, `issues-20261-group-by-shortcut`, `issues-11974`) | Updated in place to `bigint`/decimal-string expectations | Part of the accepted breaking baseline; no compat shim |
| `avg` over integer inputs returns a decimal string, not a number | Documented prominently in upgrade instructions alongside `count()` → `bigint` | The least-expected user-visible change; `toEqual(2n)` vs `2` failures make the sweep mechanical |

## Open Questions

1. **Contribution key and home for the generic descriptor type.** ~~Working position~~ **Resolved at D2 (2026-07-31):** `aggregateDescriptors` beside `codecDescriptors` on `types.codecTypes`; the declarative half (operation/input/output/nullability) lives family-neutral in framework-components so the D5 emitter can read it, and only the lowering half (`SqlAggregateDescriptor`) lives in the SQL family — the "generic base in framework, specialization in the family" pattern. *(Annotated at D5: the consumer that makes the family-neutral home necessary is the SQL family's emission SPI in `packages/2-sql/3-tooling/emitter` — which the SQL layer order forbids from importing relational-core — rather than the framework emitter as first recorded; the conclusion is unchanged and better supported, and the shared precedence rule now lives beside the vocabulary as `settleAggregateOverloads`.)*
2. **sql-builder lane registry access.** Working position: the runtime function implementations resolve through the lane context's aggregate registry exactly as the ORM does; no static codec IDs remain in the lane.
3. **Testkit access to adapter internals.** Working position: the testkits depend on their adapter package through new narrow export subpaths (the harness needs `renderLoweredSql` and the contract type, currently unexported); no source copying.
4. **SQLite testkit case API.** Working position: keep the required `storageType` field and add the `descriptor?` escape hatch the PostgreSQL harness already has, so extensions can pass unregistered descriptors on both targets.
