## 1c. A key change blocked by a foreign key on an external table

A Prisma 7 schema has no per-table control policy, so the source moved to Prisma 8 PSL first:

```
$ prisma contract print --output prisma/contract.prisma
✔ Contract written to prisma/contract.prisma
(prisma.config.ts: contract: './prisma/contract.prisma')
$ prisma contract emit           → storageHash fc063438… (unchanged)
```

The script's first plan, moving `Tag`'s key while `_PostToTag` is external, cannot be written: `contract emit` refuses it with `PSL_JUNCTION_TARGET_FK_NOT_ID` ("The junction's target-side foreign key must reference "Tag"'s full @id columns"). `Post` has the same limit. The script was changed to use a new `Profile` model that references `User`'s composite key:

```prisma
model Profile {
  id        Int     @id @default(autoincrement())
  userId    Int
  userEmail String
  bio       String?
  user      User    @relation(fields: [userId, userEmail], references: [id, email])
}
```

Planned and applied (`Create table "Profile"`, index, `Add foreign key "Profile_userId_userEmail_fkey"`), ref db → d480b1a1…, two profile rows inserted. Then `Profile` got `@@control(external)` and `User` went back to `id @id`, with `@@index([id, email], map: "User_id_email_key", unique: true)` kept as the foreign key's target. Emit → 7edbd8c2….

```
$ prisma migration plan --name user-key-back
✘ [MIGRATION.PLANNING_FAILED] Migration planning failed
  why: Primary key "User_pkey" on "public"."User" cannot change while foreign key "Profile_userId_userEmail_fkey" on "public"."Profile" references it, and the control policy does not let this plan change "public"."Profile".
→ With migration plan, give "public"."Profile" a control policy that lets this plan change it and plan again, or write the change as its own migration with prisma migration new, dropping that foreign key before the key change and adding it back after it. With db update, drop that foreign key yourself and leave it out of the contract, run db update, then add the foreign key back to both if you still want it.
exit 2
```

With `--json`, `error.meta.conflicts` holds one conflict: `kind: "foreignKeyConflict"`, `location: { entityKind: "table", entityName: "Profile", constraint: "Profile_userId_userEmail_fkey" }`. The refusal names the key, the foreign key and its table. No package was written.

## 3. Strict verify of an inferred contract with a cross-schema foreign key

New database, seeded with `CREATE SCHEMA secure; CREATE TABLE secure.owners (id int4 PRIMARY KEY); CREATE TABLE public.sessions (id int4 PRIMARY KEY, owner_ref int4 REFERENCES secure.owners(id));`.

```
$ prisma contract infer --output prisma/contract.prisma
// WARNING: Foreign key "ownerRef" -> "secure.owners" exists in the database, but its target schema is outside the introspected scope, so no relation field was generated. …
model Sessions {
  id       Int  @id(map: "sessions_pkey")
  ownerRef Int? @map("owner_ref")
  @@map("sessions")
}
$ prisma contract emit           → storageHash cae7f00c…
$ prisma db verify --schema-only --strict --json
exit 4
result.ok: false, code CONTRACT.SCHEMA_VERIFICATION_FAILED, meta.strict: true
schema.issues: [ { path: ["database","public","sessions","foreign-key:owner_ref->secure.owners(id)"],
                   actual: { nodeKind: "sql-foreign-key", name: "sessions_owner_ref_fkey", referencedSchema: "secure", … } } ]   (no expected: not-expected)
schema.warnings.issues: []
```

Exactly one issue, with the path, node kind and outcome of `SESSIONS_CROSS_SCHEMA_FOREIGN_KEY`. For contrast, `db verify --schema-only` without `--strict` reports `✔ Database schema satisfies contract` (mode "schema only (tolerant)"). Verdict: pass.

## Findings and observations

1. Finding, step 2: `db sign <migration>` does not mark the migration applied in `migration status` (`status: null`), though the `migrate resolve` reason says it "records it as applied". Either the reason should say it records the database as being at that migration's contract, or `migration status` should show the migration as applied.
2. Observation, step 1c: the `db update` advice does not mention that after the foreign key is added back, the database marker is still at the contract without it; one more `db update` or `db sign` is needed. `db verify` leads the user there.
3. Observation, step 1c: on the first `db update`, the planner warning reads "control policy suppressed: table "public.Profile" — namespace 'public' has effective control 'external' but declared 'external'". The wording contradicts itself. It is probably older than this slice.
4. Observation, step 1c: the script's `Tag` (or `Post`) key change is impossible while an implicit many-to-many junction references that model (`PSL_JUNCTION_TARGET_FK_NOT_ID`). The script now uses a `Profile` model instead.
5. Observation, all plans: `migration plan` ends with "→ Apply the migration: prisma db migrate", without `--advance-ref db`, which the example's flow and the `migrate dev` reason both need. Older than this slice.
