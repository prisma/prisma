### F-1 — 📝 Follow-up — `.include(...).aggregate(...)` type-checks and silently drops the include

**Scenario:** 6 — Exploratory
**Step:** probe "aggregate on a chain carrying an include"
**Oracle:** none scripted; charter judgement. Compared against the project's own stated principle (spec.md, coherence rationale for leaving `compileGroupedAggregate`'s signature alone this slice): "handing the grouped compile a scope it ignores would ship exactly the silent-discarded-scope shape this project exists to remove."
**Observed:**
```ts
const result = await db.Post.include('user', (u) => u.select('id'))
  .take(2)
```

```
[SQL] SELECT COUNT(*) AS "n" FROM (SELECT 1 AS "__row" FROM "public"."post" LIMIT 2) AS "post__scoped"
[PARAMS] []
OK: { n: 2 }
```
Confirmed with `pnpm typecheck` in `examples/prisma-8-demo` — the call above compiles cleanly with **no cast**, i.e. this is a fully type-safe, ordinary call, not a rare escape-hatch.

**Expected (per script):** not asserted by the script; this is exactly the "unknown unknowns in clause combinations" scenario 6 exists to surface.
**Reproduction:**
- `git rev-parse HEAD` → `1da6d16e5fafa3a2a35e84aafd37d39604b1b47e`
- `git status` at time of finding → clean except the scratch files noted in Restore
- Exact command: `pnpm exec tsx scratch-qa/scenario-6-exploratory.ts` (from `examples/prisma-8-demo`; script deleted per Restore, reproducible from the snippet above)

**Notes:** Not a regression this slice introduced — root-position `include()` + `aggregate()` is untouched by this slice's scope (the "Out" list names `select()` in aggregate position as a non-goal but doesn't mention `include()`). The silent no-op is the same *shape* of defect this project exists to eliminate, just on a clause this slice didn't touch. Given `.agents/rules/explicit-opt-in-over-diagnostics.mdc`, the house style would want either a compile-time block or a runtime diagnostic here, not silent acceptance. Worth a ticket against the ORM aggregate surface generally, not scoped to this PR.

**Expected (per script):** message should let a stranger work out what to do.
**Reproduction:**

- Compile-time half (step 3), verbatim: `test/sql-orm-client/qa-scratch-distinct-on.ts(66,70): error TS2345: Argument of type '[string]' is not assignable to parameter of type 'never'.`

**Notes:** Judgement call, not a clear failure mode from the script's list. The message names the capability (`postgres.distinctOn`) and the method (`distinctOn()`) — the `postgres.` prefix does imply "this needs a Postgres target," which is most of the remedy. This wording deliberately mirrors the sibling `sql-builder` lane's identical gate (confirmed in `collection-contract.ts:592-594` comment) — a coherence win — so changing it here alone would break that parity; if this is worth improving, it's a two-lane change, not a fix scoped to this PR. The compile-time half (`Argument of type '[string]' is not assignable to parameter of type 'never'`) is generic TypeScript output for the `never`-typed-parameter gating pattern and names nothing project-specific; that's consistent with how the codebase's other `GatedMethod`-style compile-time gates already read, not a new problem this PR introduced.

### F-3 — 📝 Follow-up — pre-existing demo command `repo-latest-per-kind` throws `BUDGET.ROWS_EXCEEDED`

**Scenario:** 3 (incidental, while confirming step 5's "compiles and runs on Postgres")
**Step:** step 5
**Oracle:** step 5 expects `.distinctOn()` to "compile and run unchanged" on a capable (Postgres) target.
**Observed:**
```
$ pnpm start -- repo-latest-per-kind
Error: Error [RuntimeError]: Unbounded SELECT query exceeds budget
  code: 'BUDGET.ROWS_EXCEEDED',
  category: 'BUDGET',
  severity: 'error',
  details: { source: 'ast', estimatedRows: 10000, maxRows: 10000 }
```
**Expected (per script):** distinctOn itself should compile and run; this command is the demo's own pre-existing example (`get-latest-user-per-kind.ts`), unrelated to distinctOn's capability gate.
**Reproduction:**
- `git rev-parse HEAD` → `1da6d16e5fafa3a2a35e84aafd37d39604b1b47e`
- Exact command: `pnpm start -- repo-latest-per-kind` from `examples/prisma-8-demo`, against the pgvector Postgres container provisioned for this run
- `ormClientGetLatestUserPerKind` (`examples/prisma-8-demo/src/orm-client/get-latest-user-per-kind.ts`) has no `.take(...)`, so the budget middleware's row estimator treats the query as unbounded and rejects it at `estimatedRows === maxRows` (10,000 == 10,000 — the boundary is treated as exceeded, not just `>`).

**Notes:** Confirmed this is unrelated to the `distinctOn` gate itself: a second, bounded reproduction (`.take(10)` added, run directly against the same DB — see F-2/F-1's SQL logs) shows `distinctOn()` compiling and executing cleanly on Postgres with native `DISTINCT ON` SQL and no capability error, satisfying scenario 3's actual oracle. This CLI command's breakage is a pre-existing gap in the demo app (missing `.take()` on an example that's been in the README's command list since before this slice), surfaced only because this was the first time in a while anyone ran it against a real budget-configured Postgres. Not introduced by, or in scope for, this PR.

## Exploratory notes (scenario 6)

Ran 8 probes against the seeded demo Postgres (charter-listed seams + a couple of adjacent ones), budget-boxed to roughly what a 30-minute charter would cover:

- `take(0)` on an aggregate → `{ total: null, n: 0 }`. Sensible, no error.
- `distinct('userId')` + `orderBy` + `cursor({ viewCount: 20000 })` + `take(2)` → cursor boundary applied as a WHERE inside the same subquery as the dedup wrap, dedup and outer ORDER BY/LIMIT still correct (`{ total: 20500 }`, matching the representatives from scenario 2). No interaction bug.
- Aggregate spec whose only selector is `count()` (no column) + pagination → inner projection uses `1 AS "__row"`, exactly as spec.md's "Inner projection" note describes. Correct.
- Two selectors reading the same column (`sum` + `max` on `viewCount`) + pagination → inner projection carries `viewCount` once (deduped by column, per spec.md), both aggregates read it correctly (`{ total: 22300, peak: 12500 }`).
- `.variant('Bug')`-narrowed collection ordered by the variant-owned `severity` column, `.take(1).aggregate(count())` → correctly emits `INNER JOIN "bug" ON "task"."id" = "bug"."id"`, orders by `"bug"."severity"`, wraps and limits. This is the MTI-variant-join fix the slice spec calls out as an operator-authorized addition ("Added 2026-08-17... The MTI variant join in `compileAggregate`") — confirmed working, not just asserted by a unit test.
- Same for `.variant('Feature')` ordered by `targetRelease` — also correct.
- `.include('user', ...).take(2).aggregate(count())` — filed as **F-1** above.
- `.skip(1)` with **no** `.orderBy()` on an aggregate — type-checks with no cast (confirmed via a second `pnpm typecheck` run), compiles to `... FROM "public"."post" OFFSET 1` with **no `ORDER BY`** anywhere in the wrap. `OFFSET` without `ORDER BY` is undefined row order in standard SQL, so this aggregate's value is not guaranteed stable across runs/vacuums. Not a defect this slice introduced (SQL semantics, and the nested/include-refinement path this slice's wrap mirrors almost certainly has the identical property for the same reason), and out of scope to fix here — logging as a candidate for a future round: consider whether `skip()`/`take()` without a preceding `.orderBy()` deserves a diagnostic project-wide, the same way `distinctOn()` without `.orderBy()` is already blocked at the type level (`State['hasOrderBy'] extends true` in the `distinctOn` signature). I did not have time within this run to check whether `take()`-without-`orderBy()` is equally permitted (I'd guess yes, since `skip()` was) — candidate for the next round.
